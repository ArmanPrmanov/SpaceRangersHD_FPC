## Poisoned frees

- Done:
  - bed870b: `platform/PoisonFrees.pas` and `--poison-frees[=MB]` (debug
    builds). A freed block is filled with `$DE` bytes and queued in a FIFO
    quarantine bounded by bytes (128 MB by default) and by blocks (one per 32
    bytes of budget), then freed; a block over a quarter of the budget is
    poisoned and freed at once. Resizes that move poison the old block, and
    the wrapped `ReAllocMem` is never called. No header of its own: sizes are
    the wrapped `MemSize`, so blocks from before the install are handled. One
    critical section guards the ring; the fill happens before it is taken. A
    double free of a quarantined block raises `EInvalidPointer`; blocks leaving
    the quarantine are checked for writes after the free, and shutdown flushes
    and logs the counts.
  - Install point: `ReadOptions` installs it right after parsing, the first
    thing `RunRangers` does. Earlier would mean parsing the flag in a unit
    initialization; the allocations before `ReadOptions` (unit initialization,
    the RTL) are the wrapped manager's blocks, so freeing them later through
    the wrapper is correct, and freeing them before the install only misses
    the quarantine for startup tables that no game object points at.
  - Release builds: the wrapper is compiled out (`{$IFOPT C+}`, the `-Sa` of
    debug builds, as `CheckSimulationThread`), and `ReadOptions` refuses the
    flag ("needs a debug build"), so a release run cannot silently go without
    it.
  - Crash reports: `LogExceptionBackTrace` (GR_Main) and the bootstrap's
    `LogExceptionTrace` add a `Poisoned frees:` line after the backtrace for an
    access violation (whether the fault address, from the Windows exception
    record, is poisoned) or an invalid pointer operation.
  - Unit tests (`tests/TestPoisonFrees.pas`) install the wrapper in the test
    process with a 64 KB budget and remove it: a freed block and a freed
    object's VMT read as the pattern, a block from before the install is
    poisoned, 256 allocations of the same size do not get a quarantined
    address back, a grown block moves and leaves a poisoned block, the budget
    holds, a write after free is found with its offset, and a double free
    raises. Release unit tests check that the wrapper is absent.
  - 32ae417: `tools/test.py --poison-frees[=MB]` passes the flag to every game
    run (headless and networked); off by default, refused with `--release`.
  - Checks: debug and release builds, the unit tests (473 checks debug, 451
    release), `check_layers.py` and `player_sites.py --check` pass.
- Not run: at the owner's request no game process was started, so these are
  owed: a single-player smoke test without the flag (nothing may change); a
  headless run with the flag (`--sim-save=... --sim-turns=5 --poison-frees`)
  that ends with `Poisoned frees: ... 0 written after free` in `Rangers.log`;
  `python tools/test.py --poison-frees` (the save suite, hot-seat, replays,
  the networked and remote-dialogue checks) with its hashes unchanged; the
  two-process `--host`/`--join` hand check with `--poison-frees` on both
  processes, including a state applied at the safe point; and the game's
  memory and speed with the flag, which were not measured.
- Known gaps: an access violation's message on Windows still says only
  "Access violation"; the `Poisoned frees:` line gives the address, and on
  macOS it can only describe the pattern (no fault address). A stale reference
  that only reads an Integer or Double field does not fault: it reads the
  pattern's value and goes on. Once a block leaves the quarantine its address
  can be reused, so a reference kept longer than 128 MB of frees is missed; a
  block larger than a quarter of the budget is reused at once. A double free
  after the block left the quarantine goes to the wrapped manager. The restart
  after a settings change does not pass the flag on. Frees are slower (each
  block is filled, and scanned when it leaves), and the ring costs 8 bytes per
  32 bytes of budget (32 MB at 128 MB).

## Fixes after the first full run

- The first `python tools/test.py --jobs 4` hung for good: every replay of a
  networked host's log with `--sim-net-talk` stopped at the day's first remote
  talk. `ReplayJob` waited on an array of the system `THandle`, 64-bit on
  Win64, while the portable `WaitForMultipleObjects` reads `Windows.THandle`,
  32-bit; it read the idle event's high half as the second handle, returned
  `WAIT_FAILED` at once and left its loop, so no talk the job asked for was
  answered and the turn thread waited for `TalkCompletedEvent` forever. Now
  `Windows.THandle`, like every other multi-event wait (d5a5628). The design
  in docs/network.md is unchanged; a replayed local talk would have hung the
  same way.
- `tools/test.py` gives every game run a timeout (30 minutes for a headless
  run or replay, `NET_TIMEOUT` from its start for a networked process); a run
  past it is killed and fails its check with a `TIMEOUT` line naming the
  command. The game and the unit test program start without a window
  (a3f8921).
- `--poison-frees` then failed the 8-human hot-seat and networked checks of
  every save at shutdown: an access violation at a poisoned address in
  `TEFilm.ReleaseObjectReferences`, from `FreeStarFilms` in `TGalaxy.Destroy`.
  It freed the star films while all stayed listed, and a scene object a film
  frees last releases itself from every listed film, the freed ones too. Each
  entry now leaves the list before it is freed, as in `KeepStarFilms`
  (36d1760).
- Pass lines, after the fixes: `3/3 saves and replays passed (windows-x64)`
  without the flag (1007 s; the first, before the film fix, 691 s) and with
  `--poison-frees` (1108 s). Goldens unchanged; the networked checks with 2
  and 8 humans pass, deterministic over two runs, with one remote talk each,
  seen by the host and by the replay of its log. `tools/unit_tests.py` (473
  checks, 0 failed), `tools/check_layers.py` and `tools/player_sites.py
  --check` pass.
